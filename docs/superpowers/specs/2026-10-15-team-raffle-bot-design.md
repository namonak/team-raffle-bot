# 쿠웨이트박 Teams 뽑기 봇 설계

작성일: 2026-10-15 · 버전: 1.0 · 대상: 프로젝트 소유자와 구현 담당자

## 1. 목적과 합의 범위

`@쿠웨이트박`은 Teams 단체 대화방에서 후보 중 원하는 수를 무작위로 뽑는 봇이다.
텍스트 직접 호출과 입력 카드 두 방식을 제공한다. 입력 카드는 추첨을 시작하면 같은 메시지에서 진행 카드와 결과 카드로 바뀐다.
캐릭터는 자신감 있고 능청스러운 아저씨이며, 사용자에게 반말로 짧고 익살스럽게 안내한다.

2026-10-15 대화에서 사용자는 아래 수정 설계와 버튼 문구를 승인했다.

- 멘션만 보내면 제목·줄바꿈 후보·추첨 개수를 입력하는 카드 표시.
- `좋아, 판 돌려!`를 누르면 새로운 카드 없이 원래 카드에서 추첨 시작.
- 공백으로 후보를 나열하는 직접 호출도 유지.
- 추첨 중 텍스트 중계를 표시하고 같은 카드에 최종 결과 보존.
- 기존 `team-meal-bot`, `team-poll-bot`의 저장소 구성과 운영 방식 재사용.

이 문서는 대화에서 승인된 설계를 구체화한 검토용 명세다. 입력 상한·만료 시간·포트·도메인은 아래에 명시한 초기 설계값이며, 실제 외부 등록·배포를 의미하지 않는다.
이번 단계의 산출물은 이 설계 문서이며, 문서 승인 후 별도 구현 계획을 작성한다.

## 2. 참조 구조와 변경 범위

두 참조 봇은 TypeScript, Express, Microsoft Agents SDK, SQLite, Docker Compose를 사용한다.
최근 `team-poll-bot`은 입력 카드를 기존 메시지 갱신으로 투표 카드로 바꾸며 이를 검증하는 SDK 연동 테스트도 갖고 있다. 이 흐름을 기준으로 삼는다. [1][2]

| 경로 | 책임과 재사용 범위 |
| --- | --- |
| `src/index.ts` | 서버, 인증, Teams 수신, 멘션 제거, 액션 전달, 카드 전송·갱신 |
| `src/domain.ts` | 입력 해석·검증, 중복 없는 무작위 추첨 |
| `src/cards.ts` | 도움말, 입력, 중계, 결과 카드와 문구 |
| `src/service.ts` | 권한·중복 요청·대화방 진행 제어, 저장과 카드 갱신 순서 |
| `src/store.ts` | SQLite 스키마와 요청·결과·반영 상태 저장 |
| `src/scheduler.ts` | 진행 단계 실행, 최종 결과 재시도와 재시작 복구 |
| `test/*.test.ts` | 각 파일 역할에 대응하는 테스트 |
| `appPackage/` | `manifest.json`, `color.png`, `outline.png` |
| `scripts/package-teams-app.sh` | 앱 ID 치환, Teams 설치 ZIP 생성 |
| `deploy/team-raffle-bot.service` | 기존과 같은 Compose 실행용 systemd 서비스 |
| 루트 설정 | `package.json`, 잠금 파일, TypeScript 설정, Dockerfile, Compose, 환경 설정 예제, 제외 파일, README |
| `docs/superpowers/specs/`, `docs/superpowers/plans/` | 설계와 구현 계획 |

Node 24 이상과 `team-poll-bot`의 빌드·테스트 명령을 기준으로 한다. 기능을 위한 새 런타임 의존성은 추가하지 않는다.
추첨에는 Node 표준 `node:crypto`를 사용한다.
투표·식사에만 필요한 테이블·명령·예약 규칙은 복사하지 않고 파일별 책임만 유지한다.
참조 저장소의 코드·DB·환경 설정은 수정하지 않는다.

현재 대상 디렉터리에는 제공된 캐릭터 PNG만 있으며 Git 저장소가 없다.
설계 기록을 위한 로컬 Git 초기화와 문서 커밋만 수행하고, 원격 저장소 생성·푸시는 이 단계에서 수행하지 않는다.

## 3. 호출과 입력

### 3.1 호출 규칙

| 입력 | 동작 |
| --- | --- |
| `@쿠웨이트박` | 입력 카드 생성 |
| `@쿠웨이트박 도움말` | 도움말 카드 표시 |
| `@쿠웨이트박 짜장 짬뽕 볶음밥` | 1개 바로 추첨 |
| `@쿠웨이트박 짜장 짬뽕 볶음밥 2` | 2개 바로 추첨 |
| `@쿠웨이트박 짜장 짬뽕 볶음밥 2개` | 2개 바로 추첨 |
| `@쿠웨이트박 서울 부산 제주 2곳` | 2개 바로 추첨 |

실제 수신 메시지에서 SDK로 봇 자신의 멘션을 제거한 뒤 해석한다.
기존 봇과 동일하게 `msteams`의 `groupChat`만 지원하고, 개인 대화와 팀 채널은 안내 후 거절한다.
일반 텍스트로 쓴 봇 이름을 임의로 제거하지 않는다.

### 3.2 텍스트 직접 호출

- 공백·탭·줄바꿈으로 후보를 구분하고 연속 공백은 하나의 구분자로 취급.
- 마지막 토큰이 정수 또는 정수 바로 뒤에 `명`, `개`, `곳`이 붙은 형태이면 추첨 개수로 사용.
- 개수 생략 시 1개. `3 명`처럼 숫자와 단위를 나눈 문법은 지원하지 않고 수정 안내.
- 음수·소수·0·안전한 정수 범위 밖 숫자 등 잘못된 개수 표기는 후보로 조용히 편입하지 않고 거절.
- 텍스트 호출의 제목은 `쿠웨이트박의 뽑기판`으로 고정. 별도 제목 문법은 추가하지 않음.
- 마지막 숫자는 항상 개수. 숫자 후보는 `1번`처럼 적도록 도움말에 안내.
- 후보명 안의 공백·따옴표 묶음은 지원하지 않음. 공백 포함 이름은 입력 카드 이용.
- `도움말` 단독은 예약 명령. 해당 단어를 후보로 쓰려면 카드에서 입력.

### 3.3 입력 카드

| 필드 | 규칙 |
| --- | --- |
| 뽑기 제목 | 필수, 앞뒤 공백 제거 후 1~100자 |
| 후보들 | 필수, 여러 줄 입력, 한 줄에 후보 하나 |
| 추첨 개수 | 기본값 1, 필수, 양의 정수. 카드에서는 단위 없이 숫자 입력 |
| 시작 버튼 | `좋아, 판 돌려!` |

카드 후보는 줄별 앞뒤 공백을 제거하고 빈 줄은 무시한다. 이름 내부 공백은 보존한다.
줄 끝의 숫자도 후보 이름의 일부이며 개수는 별도 필드에서만 읽는다.
입력란에는 접근성을 위한 label과 필수값 안내를 제공한다.
작성자를 안내하고 `@쿠웨이트박 도움말`과 텍스트 호출 예시를 짧게 표시한다.
카드는 투표곰과 같은 Adaptive Card 1.5와 `Action.Execute` 패턴을 기준으로 한다. [2]

입력 카드를 연 사용자만 시작 가능하며 카드의 유효기간은 24시간이다.
작성자·대화방·메시지 ID·만료 여부는 서버 저장값으로 검사한다. 액션 payload의 사용자 정보는 신뢰하지 않는다.
오류 시 invoke 오류 응답으로 수정 이유를 알리고 입력 카드를 교체하지 않는다.
다른 사용자가 누른 오류도 공유 카드 전체를 바꾸지 않는다.
실제 Teams에서 오류 표시와 작성 중 값 유지 여부를 검증한다.

### 3.4 공통 검증

두 입력을 같은 제목·후보 배열·개수 형태로 정리한 뒤 아래 규칙을 공통 적용한다.
문자 수는 JavaScript 문자열 코드 단위가 아니라 유니코드 코드 포인트로 계산한다.

| 조건 | 처리 예시 |
| --- | --- |
| 후보 2개 미만 | `혼자 나와 놓고 뭘 뽑아. 둘은 데려와.` |
| 후보 50개 초과 | `판이 너무 크다. 후보는 쉰까지 데려와.` |
| 후보당 50자 초과 | 이름을 50자 이내로 줄이도록 안내 |
| 전체 입력 3,000자 초과 | 제목·후보·개수 입력 합계를 줄이도록 안내 |
| 동일 후보 반복 | `같은 이름으로 두 번 들어왔네. 한 자리씩만 서자.` |
| 개수 0·음수·소수·잘못된 형식 | `몇 개 뽑을 건지 양의 정수로 딱 정해봐.` |
| 개수 > 후보 수 | 후보 수와 요청 개수를 설명하고 수정 안내 |
| 개수 = 후보 수 | `전부 뽑으면 추첨이 아니지. 뽑을 수를 줄여봐.` |
| 제목·필드 타입 변조 | 유효한 입력을 다시 요청하며 추첨 미실행 |

이름은 앞뒤 공백 제거 및 유니코드 NFC 정규화 후 정확히 같은 문자열이면 중복으로 간주한다.
영문 대소문자와 내부 공백 차이는 자동으로 합치지 않는다.
카드의 클라이언트 검증과 무관하게 서버에서 모든 규칙을 다시 검사한다.
사용자 텍스트는 카드 Markdown·HTML 표현을 이스케이프하고 제어 문자를 검증해 표시 왜곡을 막는다. 링크·실제 사용자 멘션으로 변환하지 않는다.

## 4. 같은 카드에서의 추첨

입력 카드는 종이 한 장의 내용을 고쳐 쓰듯 같은 Teams 메시지 ID로 갱신한다.
시작 액션 이후에는 `sendActivity`로 진행·결과 카드를 추가 발송하지 않는다.
텍스트 직접 호출은 진행 카드 한 장을 최초 게시한 뒤 그 메시지만 갱신한다.

| 단계 | 표시 |
| --- | --- |
| 입력 | 제목·후보·개수·시작 버튼 |
| 시작 | 제목, 후보 수와 추첨 수, `자, 판 돌린다. 운들 챙겨왔나?` |
| 중계 | 후보를 번갈아 언급하는 역전 문구, 후보 간 우열은 연출임을 작은 안내로 표시 |
| 결과 | 제목, 당첨자 전원, `오늘 운 좀 좋은데?` |

정상 상태에서 약 1.5~2초 간격의 4~5단계, 약 6~10초를 연출 목표로 한다.
정확한 간격·모든 중간 장면의 노출은 네트워크와 Teams 클라이언트에 따라 달라지며 보장하지 않는다.
중계 문구는 템플릿으로 만들고 외부 LLM 호출은 사용하지 않는다.
복수 추첨도 한 카드에서 중계 후 당첨자 전원을 표시한다. 결과 순서는 순위가 아니라고 안내한다.
진행·결과 카드는 텍스트만 포함하고 입력란·버튼·이미지·재추첨 버튼을 넣지 않는다.
새 추첨은 텍스트 호출 또는 새 입력 카드로 시작한다. 완료 결과는 덮어쓰지 않는다.

중계 후보 선택은 실제 당첨 확률에 영향을 주지 않는다.
전체 후보에 같은 기회를 부여해 `crypto.randomInt`를 이용한 부분 Fisher–Yates 방식으로 중복 없이 원하는 수를 추출한다.
선택 결과는 연출 전에 한 번 확정·저장하며, 카드 재시도나 프로세스 재시작으로 재추첨하지 않는다.

## 5. 처리 순서와 상태 저장

### 5.1 데이터와 경계

SQLite에는 아래 최소 정보만 보관한다. 투표 응답·마감·식사 일정 테이블은 만들지 않는다.

| 데이터 | 핵심 저장 내용 |
| --- | --- |
| 대화방 | 대화방 ID, SDK 대화 참조 |
| 입력 카드 | ID, 작성자 ID, 대화방 ID, 메시지 ID, 생성 시각, 게시 상태, 생성 요청 ID |
| 추첨 | ID, 시작 요청 키, 입력 카드 ID 또는 직접 호출 ID, 제목, 후보, 개수, 확정 당첨자, 대화방·작성자 ID, 메시지 ID, 게시·진행·결과 반영 상태, 다음 처리 시각 |

텍스트 요청 키는 대화방 ID와 수신 activity ID로 구성하고, 카드 시작은 입력 카드 ID에 유일 제약을 둔다.
입력 카드 생성 요청도 activity ID로 중복을 방지한다. 필수 수신 ID가 없으면 추첨·게시를 시작하지 않는다.
텍스트 요청 중복 확인은 재추첨에 앞서 수행한다.
동일 카드에서 다른 입력값을 재전송해도 최초로 접수된 추첨 결과를 유지한다.

동시에 같은 방에서 새 추첨 두 개를 시작하지 않는다. 입력 카드 여러 장을 열 수는 있으나 시작은 대화방별로 직렬 처리한다.
이미 진행 중이면 `지금 판 돌아가잖아. 이것부터 끝내고 가자.`로 거절한다.
진행 종료는 최종 결과 갱신 시도까지를 뜻한다. 결과 반영만 지연된 과거 작업은 복구 대상으로 두고 새 추첨을 영구 차단하지 않는다.
게시 여부가 불확실한 작업이 남은 방은 운영자가 확인하기 전 추가 추첨을 막는다.
단일 프로세스·단일 컨테이너 운영을 전제로 한다.

### 5.2 시작과 실행

1. 요청 형식·대화방·사용자·중복 여부 검사.
2. 입력 카드 경로이면 소유권·메시지 ID·만료 여부 추가 검사.
3. 공통 입력 검증 및 같은 방의 진행 작업 확인.
4. 동기 SQLite 트랜잭션에서 결과와 추첨 상태 저장. 트랜잭션 중 네트워크 호출 금지.
5. 카드 경로는 기존 메시지를 갱신. 직접 호출은 최초 진행 카드를 게시하고 응답 메시지 ID 저장.
6. 이후 단계는 저장된 다음 처리 시각을 바탕으로 실행. 수신 HTTP/invoke 응답을 연출 종료까지 붙들지 않음.
7. 정상적으로 텍스트 중계 후 최종 결과 갱신. 성공 후 반영 완료 기록.

기존 `scheduler.ts` 역할 안에서 진행 작업은 짧은 주기로 확인하되 겹쳐 실행하지 않는다.
중계 실행과 결과 재시도 모두 추첨별 갱신 순서를 보장한다.
복구된 결과를 뒤늦은 중계가 덮어쓰지 못하도록 저장 상태를 다시 확인한다.
종료 시 새 작업을 멈추고 처리 중 DB 접근이 끝난 뒤 연결을 닫는다.

### 5.3 장애와 복구

- 최초 카드 게시 전에 게시 시도 상태를 기록. 정상 응답 시에만 메시지 ID 연결.
- 최초 게시의 응답 유실이나 게시 직후 종료는 `게시 확인 필요` 상태로 남김. 메시지 ID를 모르는 상태에서 자동 재게시하지 않음.
- 명확한 게시 거절도 같은 수신 요청을 즉시 자동 재전송하지 않고 오류를 안내. 수정 후 새 호출로 진행.
- 이미 메시지 ID가 있는 카드 갱신은 같은 ID로만 재시도. 결과 카드 추가 전송 금지.
- 중계 갱신 실패 시 남은 연출을 생략하고 저장된 최종 결과 반영 우선.
- 429는 Retry-After를 존중하고, 일시 오류는 대기 시간을 늘려 재시도. 주기 작업이 무한 고빈도 재요청하지 않도록 다음 재시도 시각 저장. [3]
- 재시작 시 메시지 ID가 있는 미완료 추첨은 중계 재생 없이 확정 결과로 마무리.
- 삭제된 메시지·권한 상실 등 영구 오류는 자동 반복을 중단하고 운영 확인 상태로 기록. 로그에 작업 ID와 오류 분류를 남김.
- 입력 카드의 최초 게시가 불확실하면 추첨을 허용하지 않음. 미연결 카드 복구 또는 취소 절차는 README에 설명.
- 운영 확인은 저장된 결과를 유지한 채 메시지 ID 연결 또는 게시되지 않았음 확인 후 취소. 결과를 임의로 다시 생성하지 않음.

## 6. 명령 제안·캐릭터·아이콘

참고 이미지처럼 두 입력 예시와 설명을 manifest의 `bots[].commandLists`에 추가하는 것을 목표로 한다.
현재 참조 봇 manifest에는 commandLists가 없으므로 이 설정은 기능상 필요한 추가다.
기존 manifest 1.22를 기준으로 해당 스키마를 검증하며, 표시를 위해 버전·구조 변경이 필요하면 먼저 사용자에게 알린다.
동적 사용자 후보를 제안 목록에서 자동 완성하는 기능은 만들지 않는다.
실제 제안 위치·형태는 Teams 클라이언트에서 확인한다.

| 제안 예시 | 설명 |
| --- | --- |
| `홍길동 김철수 이영희` | `후보를 띄어 적어. 내가 하나 뽑아주지.` |
| `홍길동 김철수 이영희 2명` | `마지막에 몇 명 뽑을지만 붙여.` |

말투는 짧고 자신감 있게 유지하되 오류에서는 수정 방법을 분명히 안내한다.
욕설·모욕·실제 승률처럼 보이는 임의 수치는 사용하지 않는다.

제공된 루트 PNG를 바탕으로 아래 두 아이콘을 제작한다. 초기 설계에서는 원본을 보존했으나, 2026-10-15 사용자 요청에 따라 아이콘 생성 완료 후 루트 원본을 삭제한다.

| 파일 | 초기 제작 규격 |
| --- | --- |
| `appPackage/color.png` | 192×192 PNG. 곱슬머리·선글라스·콧수염 중심으로 작은 크기 식별성 확보 |
| `appPackage/outline.png` | 32×32 PNG. 투명 배경과 흰색 단색, 얼굴 특징을 단순화 |

아이콘 제작·편집에는 ImageGen을 사용하고 실제 해상도와 색·알파를 검증한다.
진행 카드에는 캐릭터 이미지를 추가하지 않는다.

## 7. 운영 설정과 보안

| 항목 | 설계값 |
| --- | --- |
| 앱 이름·콜네임 | `쿠웨이트박`, `@쿠웨이트박` |
| 컨테이너·이미지·서비스 | `team-raffle-bot` |
| 컨테이너 포트 | `3978` |
| 호스트 바인딩 | `127.0.0.1:3980` — 기존 3978·3979와 분리하는 제안값 |
| 운영 도메인 | `raffle-bot.namonak.dev` — 등록 전 제안값 |
| endpoint | `/api/messages`, `/healthz` |
| DB | 개발 `./data/team-raffle-bot.sqlite`, 컨테이너 `/data/team-raffle-bot.sqlite` |
| Compose 볼륨 | `raffle-data` |
| Teams ZIP | `dist/team-raffle-bot-YYYYMMDD-HHMMSS.zip`, 한국 시간 |

환경 변수 이름은 `MicrosoftAppId`, `MicrosoftAppPassword`, `MicrosoftAppTenantId`, `PUBLIC_BASE_URL`, `DATABASE_PATH`, `PORT`를 유지한다.
쿠웨이트박용 별도 앱 등록을 사용하며 기존 봇의 ID와 비밀값을 복사하지 않는다.
인증 필수값 누락 시 시작을 거부하고 Teams endpoint에 JWT 검증과 요청 크기 제한을 유지한다.
ZIP에는 치환된 manifest와 아이콘 두 개만 담는다. 비밀값·DB·로그는 Git이나 ZIP에 포함하지 않는다.
DB에는 후보와 사용자·대화방 식별자가 있으므로 기존 방식대로 접근을 제한하고 중지 후 백업한다.
초기 버전은 기록을 자동 삭제하지 않는다. 보존 기간 정책·관리 화면·다중 인스턴스 운영은 범위 밖이다.

## 8. 검증과 완료 기준

| 구분 | 핵심 확인 |
| --- | --- |
| 입력 | 빈 멘션·도움말, 기본 1개, 숫자·명·개·곳, 공백·줄바꿈 차이, 숫자 후보 해석 |
| 경계값 | 후보 0·1·2·50·51개, 개수 0·음수·소수·과대·전체 선택, 중복·정규화·길이·변조 타입 |
| 추첨 | 요청한 수, 원래 후보만 선택, 중복 없음, 고정 난수 입력으로 선택 경계 확인. 불안정한 통계 테스트 제외 |
| 카드 | 제목·라벨·기본값·문구·이스케이프, 진행·결과에 입력·액션·이미지 없음 |
| 권한·중복 | 타인·다른 방·만료 카드 거절, 이중 클릭·중복 activity·동시 호출에서 최초 결과 유지 |
| 저장·복구 | 닫고 다시 열어도 결과 유지, 최초 게시 불확실성, 429·일시 실패·영구 실패, 중계가 결과를 덮어쓰지 않음 |
| SDK 연동 | 입력 카드와 모든 갱신의 메시지 ID 동일, 시작 후 추가 sendActivity 0회, invoke 응답 지연 없이 중계 예약 |
| 서버 | 필수 인증값 누락 거부, 인증 없는 요청 거부, healthz, 종료 처리 |
| 배포·패키지 | 아이콘 크기·알파·색, ZIP 내용·ID 치환, test/typecheck/build, 가능한 환경에서 Compose·Docker 확인 |

실제 Teams에서는 두 사용자로 입력 카드 소유권, 오류 시 입력 유지, 빠른 이중 클릭, 텍스트·카드 추첨, 단일·복수 결과를 확인한다.
데스크톱·모바일에서 제안 목록, 줄바꿈, 같은 카드 전환과 중계 속도를 확인한다.
실제 앱 등록·배포·테넌트 설치 검증은 로컬 자동 테스트로 대체하지 않는다.

완료 기준은 두 진입 경로가 같은 추첨 규칙을 지키고, 시작부터 결과까지 카드 한 장을 유지하며, 장애 후에도 이미 확정된 당첨자를 바꾸지 않는 것이다.
이 문서 승인 후 파일별 구현 순서와 확인 명령을 별도 구현 계획으로 작성한다.
